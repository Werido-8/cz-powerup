# 知识库权限模型与管理流程核查报告

## 1. 权限模型总览

### 1.1 公共知识库

定义：面向全体系统用户开放浏览的知识库，用于规章制度、公共制度、通用资料等全员可见内容。

推荐权限：

| 主体 | 权限 |
| --- | --- |
| 全体系统用户 | 浏览 |
| 知识库管理员 | 上传、管理 |
| 系统管理员 | 管理 |

实测 Demo：公共库“规章制度汇编库”点击权限后打开“权限说明”，只读展示全体系统用户浏览、知识库管理员上传/管理、系统管理员管理；未允许添加角色或成员。该方向正确。

### 1.2 专业知识库

定义：仅指定角色和成员可访问的知识库，用于运行、调度、设备、交易等专业资料。

授权方式：

- 角色授权：给角色批量授予浏览、上传或管理。
- 个人授权：给具体成员直接授予浏览、上传或管理。
- 最终权限：角色权限与个人权限中的最高级。

权限级别：

| 权限 | 能力范围 |
| --- | --- |
| 浏览 | 查看知识库、搜索文件、预览文件、下载文件 |
| 上传 | 在浏览基础上，向知识库提交上传，查看自己的上传状态，提交更新版本；非个人库上传需审批 |
| 管理 | 在上传基础上，管理库内文档、编辑知识库、配置权限、审批上传、处理库内异常 |

实测 Demo：权限代码和页面均使用 `管理 > 上传 > 浏览` 递进关系，成员授权表展示“角色权限 / 个人权限 / 最终权限”。

### 1.3 创建人默认权限

Demo 源码 `createInitialGrants()` 将当前用户“张工”作为新建专业库默认管理者。实测新建专业库第二步显示“管理者 1 人、单独授权成员 1 人”。

推荐：创建人自动获得管理权限，但后续可转交；保存时必须至少保留一名管理者。

### 1.4 最后一名管理员保护

Demo 成员移除逻辑有 `hasManager()` 校验；创建和编辑类型变更也校验至少一名管理者。实测移除“知识库管理员”角色没有二次确认，但没有触发最后管理员场景，因为张工个人仍是管理者。

推荐：角色移除、成员移除、降权、批量导入覆盖、类型变更保存都必须统一校验至少一名管理者。

## 2. 创建知识库流程

### 2.1 正式推荐流程

```text
公共库：
基本信息 -> 创建

专业库：
基本信息 -> 权限分配 -> 创建知识库
```

### 2.2 Demo 实际流程

公共库：

- 类型切换为公共知识库。
- 显示默认权限说明。
- 隐藏权限配置步骤。
- 底部按钮为“创建知识库”。

专业库：

- 默认选择专业知识库。
- 显示步骤条：基本信息、权限分配。
- 下一步前校验挂载目录和名称。
- 权限分配复用 `PermissionEditor`。
- 创建人默认管理。

### 2.3 差异与风险

- 同名校验、名称长度、后端唯一性未接入。
- 挂载目录选择器只显示目录节点，这点正确；需后端也校验不能挂到知识库叶子节点。
- 创建结果只进入前端内存 store，刷新后不可靠。

## 3. 编辑知识库流程

编辑知识库应只修改基本信息：

- 知识库名称。
- 挂载目录。
- 知识库简介。
- 类型变更。
- 只读权限概览。

实测 Demo：编辑专业库弹窗显示“权限概览”，并提示“权限配置请通过知识库列表中的「权限」入口进行管理”。未把完整授权表塞入编辑弹窗，符合推荐产品关系。

当前问题：

- 保存只走前端内存。
- 类型变更时保存后的后端权限处理未定义。
- 公共转专业后权限配置完成，但点击保存前的中间状态如何持久化待设计。

## 4. 独立权限配置流程

专业库独立权限配置入口包含：

```text
库清单 -> 专业库行内“权限” -> 权限配置弹窗
```

实测能力：

- 权限概览：授权角色、单独授权成员、管理者、待处理申请。
- 角色授权：添加角色、搜索角色、设置权限等级、移除角色。
- 成员授权：添加成员、搜索成员、筛选直接授权、设置个人权限、展示最终权限。
- 权限申请：展示待处理申请，当前并网运行管理库为空态。
- 保存方式：统一点击“保存配置”；Demo 保存为 toast/组件状态，未接后端。

权限冲突规则：

```text
最终权限 = max(角色权限, 个人直接权限)
```

例子：

```text
运行值班员角色：浏览
张工个人权限：上传
张工最终权限：上传
```

## 5. 类型变更规则

### 5.1 公共转专业

应有规则：

- 弹出风险提示。
- 说明全员浏览将失效。
- 必须配置角色或成员权限。
- 至少一名管理者。
- 完成权限配置后才允许保存。

Demo 表现：有“变更为专业知识库？”确认，继续后进入权限配置，保存前校验至少一名管理者。符合推荐方向。

### 5.2 专业转公共

应有规则：

- 弹出风险提示。
- 说明全体系统用户将获得浏览权限。
- 说明原角色和个人授权如何处理。
- 有二次确认。

Demo 表现：确认文案说明“当前角色和成员的自定义授权将停止生效，历史配置将保留，便于以后恢复为专业库”。该策略合理但正式需求未定义，需产品和后端确认。

| 17. 专业库切换为公共库如何处理历史权限 | Demo 说历史配置保留但停止生效；正式需求待确认 |
| 18. 权限申请是否属于权限配置弹窗 | Demo 属于权限配置页签，同时审批台也有权限申请；双入口关系需确认 |
| 19. 权限申请由谁审批 | 一期由知识库管理员审批 |
| 20. 当前 Demo 哪些规则只做 UI | 角色/成员来源、权限保存、审批通过/驳回、上传、解析重试、下载、预览均未接真实后端 |

## 7. 当前问题

1. 权限定义在正式文档中只有“仅查看/可上传/可管理”，页面使用“浏览/上传/管理”，建议统一词汇。
2. 公共库和专业库的业务定义应单独成节，避免开发按按钮猜规则。
3. 权限申请同时出现在审批台和权限配置弹窗，需明确是否同一待办池。
4. 公共库上传权限是否允许额外配置未定义。
5. 专业转公共后的历史权限处理未定义。
6. 最后一名管理员保护需要覆盖角色移除、角色降权、成员降权、保存提交，而不只是成员移除。
7. 审批台高风险操作缺少确认，单条通过直接移除。
8. 当前权限保存无后端持久化和审计。

## 8. 推荐方案

### 8.1 产品口径

```text
编辑知识库负责管理知识库自身属性；
权限配置负责管理谁可以进入，以及进入后可以做什么；
新建专业库时复用权限配置能力，但已有知识库的权限维护通过独立入口完成。
```

### 8.2 后端模型

建议后端至少包含：

- `knowledge_base`：知识库基础信息、类型、状态、分类、创建人。
- `knowledge_base_role_grant`：库、角色、权限级别。
- `knowledge_base_member_grant`：库、人员、直接权限级别。
- `knowledge_permission_request`：申请人、目标库、申请权限、理由、状态、审批人、审批意见。
- `knowledge_audit_log`：权限变更、类型变更、启停、删除、审批等审计。

### 8.3 权限计算

后端统一计算最终权限，前端只展示结果：

```text
roleLevel = 用户所有角色在该库上的最高权限
directLevel = 用户个人直接授权
effectiveLevel = max(roleLevel, directLevel)
```

公共库特殊处理：

```text
effectiveLevel >= 浏览，适用于全体系统用户；
上传/管理仍按管理员角色或系统管理权限判定。
```

### 8.4 验收要点

- 公共库打开权限为只读说明，不允许配置角色/成员。
- 专业库创建必须至少一名管理者。
- 专业库成员表必须显示角色权限、个人权限、最终权限。
- 移除或降权最后一名管理者必须阻止。
- 审批、重试、删除、停用、类型变更必须二次确认并产生审计。
- 前端和后端都必须执行权限校验，不能只靠页面隐藏按钮。
