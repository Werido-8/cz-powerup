> **会议性质**：知识库业务需求评审 + 界面方案讨论

## 一、会议结论速览

| 事项 | 结论 |
| --- | --- |
| 需求写法 | 先写**用户视角的业务需求**（能看什么、能做什么），再补系统实现需求；**不要以页面入口堆需求** |
| 本期范围 | **大幅简化**：不做过多部门层级；先一个管理员体系；上传审批驳回后**重新开单上传**即可，不做复杂重传历史 |
| 空间结构 | 本期**弱化/取消「部门」产品概念**；用分类（公共 / 专业等）+ 多个知识库；权限落到**知识库**，不落到分类 |
| 权限 | 知识库可授给**角色**和/或**个人**，两路合并；默认可公开绑定某角色，避免给几百人逐个配 |
| 文件级操作 | 普通用户：查看/预览/下载；**删除/编辑归管理员**；上传人也不能随便删（审批未结束可撤回——本期也可先不做撤回） |
| 库内目录层级 | **本期不分层级**；靠检索；多版本不走列表子表格，走历史版本 |
| 下一步 | 2 号按简化思路**重新整理业务需求** → 再系统设计；可先出首页等高保真再逐页讨论 |

## 二、议题与问题清单

### 2.1 需求该怎么写？（方法论，贯穿全会）

| # | 问题/议题 | 结论 |
| --- | --- | --- |
| R-01 | 「知识总览」和「所有文档」是否同一功能、是否该拆成两个入口需求？ | 评审认为从业务上不必按入口拆；应描述：能看全部有权/无权库（库内无权限仍可知存在并可申请）；能看有权文档列表并过滤检索 |
| R-02 | 需求应按入口还是按角色写？ | **按角色 + 业务能力**写（普通用户 / 管理员等），入口只是交互设计结果 |
| R-03 | 查看文件下的下载、收藏、历史版本、内容检索是否要拆成多条「独立需求」？ | 宜作为**「查看文件」下的子能力**分层描述，不必每个交互点一条独立需求 |
| R-04 | 「切换知识库」要不要写成独立需求？ | 可隐含在查看文件/文件列表过滤中；不要无上下文的独立功能条目 |
| R-05 | 「最近访问只保留最近 5 个」是否合理？ | **不必硬限制条数**；数据可持续存，默认展示 5/10，点「更多」看全部 |

---

### 2.2 信息架构与入口是否重复？

| # | 问题/议题 | 结论 |
| --- | --- | --- |
| IA-01 | 知识总览（左树+右库文件）与全部文档（顶栏过滤、跨库列表）是否重复？ | **倾向于合并**：选根/「全部」= 跨库全部资料；点某库 = 该库文件；不必再单独做「全部资料」整页 |
| IA-02 | 「我的空间」是否要独立一整套，还是与总览整合？ | 倾向**同一工作台**：点「我的空间」相当于把左侧定位到个人库/过滤条件；最近访问、我的上传、收藏可作入口或快捷过滤，不必另起一套全页 |
| IA-03 | 「全部资料」菜单是否还要？ | 评审倾向**可去掉**；用总览根节点/「全部」替代跨库列表 |
| IA-04 | 无权限的库是否展示？ | **要展示**（可申请），否则用户不知道有什么可申请 |
| IA-05 | 知识库 / 文档能否置顶、进快速访问？ | **可以**；快速访问可固定库，也可固定常用文档（参考 GPT 类快捷） |

---

### 2.3 文件预览与切换交互

| # | 问题/议题 | 结论 |
| --- | --- | --- |
| UX-01 | 预览页是否要在当前页频繁切换到其他库？ | **不推荐**作为主路径；库内切文件可以；跨库更合理是回列表再开，或用多标签/多浏览器 Tab 对比 |
| UX-02 | 预览布局：左侧当前库文件列表 + 中间预览是否合适？ | 库内切换文件可接受；全屏预览诉求存在；不要在预览页同时堆过多侧栏导致有效预览区过小 |
| UX-03 | 在预览页切换知识库后默认行为？ | **不要**默认打开第一个大文件；也不宜保留上一库文件；折中「清空预览占位」则切换意义变弱 → **结论：别在预览页做库切换** |
| UX-04 | 打开文件用当前页还是新 Tab？ | 倾向**默认新开 Tab**；可选全局/用户配置「当前窗 or 新窗」（可后续做） |
| UX-05 | 卡片上给普通用户展示编辑/删除？ | **不展示**；仅预览、下载；删除/隐藏等到**知识库管理**侧统一做 |

---

### 2.4 部门 / 管理员 / 权限（范围砍伐重点）

| # | 问题/议题 | 结论 |
| --- | --- | --- |
| P-01 | 是否要部门管理员 + 公共管理员两层？ | **本期不要两层**；先设（一个或少数）管理员管公共空间新建库、上传审批等；分层授权留 2.0 |
| P-02 | 是否还要「部门知识库」产品概念？ | **本期不做部门概念**；界面可不体现部门；若以后做部门需与组织机构打通（人员调动跟权），太重 |
| P-03 | 公共空间下多个库怎么管？ | 公共分类下可建多个库；按专业方向需要再建即可，不必先绑部门树 |
| P-04 | 权限挂在分类还是知识库？ | **挂在知识库**；分类仅组织浏览 |
| P-05 | 是否所有库默认对全员开放？ | 可设计**默认公开**（绑默认角色），同时支持按角色/人精细授权；不能假定「公共 = 人人都能进任意库」而无差别 |
| P-06 | 个人申请某库权限 vs 角色授权如何并存？ | **两路都通**：角色→库、个人→库；分配权限 UI 要同时支持指定人/指定角色，访问结果取并集 |
| P-07 | 文件级是否拆「仅查看 / 可下载」等？ | 本期观点：能看与下载区分意义不大；**编辑、删除禁止普通用户**即可 |
| P-08 | 上传者能否删除自己的文件？ | **审批通过后也不能由上传者随便删**；未审批可撤回——但本期也可**先不做撤回**，简单做 |

### 2.5 审批与上传流程

| # | 问题/议题 | 结论 |
| --- | --- | --- |
| A-01 | 驳回后是否要带着历史记录/意见重传同单？ | **本期不做复杂版**：驳回后重新发起上传即可；真有需求再改模块 |
| A-02 | 「我的上传」入口放哪？ | 菜单可单独有「我的上传」（可发现性）；也可靠「我的空间」进入；上传动作可在选中库时触发，也可在「我的上传」里选库后传；**允许多入口** |
| A-03 | 传个人库 vs 公共库交互是否不同？ | 个人库可就地传；公共库走选库/审批；上传相关状态（审批进度）应能在上传空间内看到 |

---

### 2.6 检索、标签与「全部库」性能

| # | 问题/议题 | 结论 |
| --- | --- | --- |
| S-01 | 跨库「全部」时标签筛选怎么办？标签按库维度不同 | **选「全部」时隐藏标签等库维度筛选项**；选单库后再显示并跟随该库 |
| S-02 | 跨库列表排序（名称、大小、时间等）性能是否够？ | 认可是后续要处理的问题；索引/缓存（如 Redis）可考虑；文件元数据在表/ES 侧具体实现时再定 |
| S-03 | 文档要不要库内多级目录？ | **本期不分**；多目录难归类；若以后加分类可能牵涉 RAG 源码改动，越加越麻烦 → 靠检索 |

### 2.7 其它界面细节

| # | 问题/议题 | 结论 |
| --- | --- | --- |
| UI-01 | 多版本是否用列表子表格展开？ | **不建议子表格**（版本多时拖慢列表）；用历史版本入口足够 |
| UI-02 | 知识库信息（标签、更新时间、描述）布局 | 可压到右侧/标题旁浅底，省纵向空间 |
| UI-03 | 卡片视图是否必要？ | 卡片视图**意义不大**；保留表格 + 预览/下载/更多即可（可暂留开关） |
| UI-04 | 本期优先出哪些页面？ | 先做**首页（知识总览）、全部资料（若保留）、我的空间**；管理端等后续 |

## 四、本期明确不做（砍掉清单）

1. 部门管理员 × 公共管理员双层权限体系，以及与组织机构深度绑定  
2. 产品结构上的「部门知识库」树（改用分类/专业下建多个公共库）  
3. 驳回带历史的复杂重传；复杂「撤回」流程（可先极简）  
4. 库内多级目录分类；列表多版本子表格展开  
5. 普通用户在浏览端的编辑/删除入口  
6. 独立整页「全部资料」（用总览根节点替代，除非方案证明仍有必要）
