## 结论：权限配置应当独立，但在“新建专业库”流程中复用

不建议把完整权限配置塞进“编辑知识库”弹窗。权限配置涉及角色、成员、权限申请、继承关系，复杂度远高于名称、简介等基本信息，放在一起会让编辑弹窗过重。

推荐关系：

* **新建知识库**：根据知识库类型，动态决定是否进入权限配置步骤。
* **编辑知识库**：只管理基本信息和类型变更。
* **权限配置**：作为独立的大弹窗，由列表中的“权限”入口打开。
* 新建专业库时，复用同一套权限配置组件，而不是再写一套权限表单。

```text
新建公共知识库
基本信息 → 确认创建

新建专业知识库
基本信息 → 权限分配 → 确认创建

编辑知识库
只编辑基本信息

权限配置
从知识库列表“权限”按钮独立打开
```

# 一、先统一权限模型

建议将权限级别设计为递进关系，每个角色或成员只选择一个最高级别。

| 权限级别 | 能力范围                        |
| ---- | --------------------------- |
| 浏览   | 查看、搜索、预览、下载知识库中的文件          |
| 上传   | 包含浏览权限；可上传文件、查看自己的上传和处理进度   |
| 管理   | 包含浏览和上传；可维护文件、目录、状态及知识库成员权限 |

权限优先级：

```text
管理 > 上传 > 浏览
```

同一个人可能同时通过“角色”和“个人授权”获得权限，最终生效权限取最高值。

例如：

```text
运行值班员角色：浏览
张工个人授权：上传

张工最终权限：上传
```

首版不建议加入“拒绝权限”或复杂权限覆盖规则，否则容易让管理员看不懂实际权限。

## 公共知识库

公共知识库不开放自定义成员权限配置，采用固定策略：

```text
全体系统用户：浏览
知识库管理员：上传和管理
系统管理员：管理
```

界面中只展示固定权限说明，不展示角色、成员授权表格。

## 专业知识库

专业知识库必须配置权限，支持：

* 按角色授权；
* 按具体成员授权；
* 查看最终生效权限；
* 处理权限申请。

创建人默认成为管理者，且至少保留一名管理者。

## 3. 类型不建议直接用普通下拉框修改

知识库类型变化会影响整个权限模型，因此类型字段建议默认只读，并提供“变更类型”操作。

### 公共库变更为专业库

点击后提示：

```text
变更为专业知识库？

变更后，知识库将不再对全体用户开放，
必须重新配置角色和成员权限。

取消    继续配置权限
```

随后进入权限配置流程，只有权限配置完成后才能保存类型变更。

### 专业库变更为公共库

提示：

```text
变更为公共知识库？

变更后，全体系统用户将获得浏览权限。
当前角色和成员的自定义授权将停止生效，
历史配置将保留，便于以后恢复为专业库。

取消    确认变更
```

建议保留历史权限配置，而不是直接删除。

## 4. 编辑弹窗中是否展示权限

可以展示一张只读概览卡，但不要在这里直接编辑：

```text
权限概览
专业知识库 · 3 个授权角色 · 8 名授权成员 · 2 名管理者

权限配置请通过知识库列表中的“权限”入口进行管理。
```

这样用户知道当前权限状况，又不会让编辑弹窗过度复杂。

当前右侧窄抽屉的问题是：

* 宽度不足；


不要使用过大的虚线空状态框占据半个页面。

# 六、列表页三个入口的关系

知识库列表操作建议保持：

```text
编辑    权限    更多
```

* **编辑**：打开基本信息弹窗；
* **权限**：打开独立权限配置弹窗；
* **更多**：停用、启用、复制链接、删除等低频操作。

新建知识库内部使用同一套权限组件：

```text
PermissionEditor
```

但不同场景提交方式不同：

```text
新建专业库：完成权限后创建知识库
独立权限配置：保存已有知识库的权限变更
公共知识库：只读显示默认权限说明
```

# 七、推荐的最终信息架构

```text
知识库管理
│
├─ 新建知识库
│  ├─ 基本信息
│  ├─ 公共库 → 直接创建
│  └─ 专业库 → 权限分配 → 创建
│
├─ 编辑知识库
│  ├─ 名称
│  ├─ 目录
│  ├─ 部门
│  ├─ 简介
│  └─ 类型变更
│
└─ 权限配置
   ├─ 权限概览
   ├─ 角色授权
   ├─ 成员授权
   └─ 权限申请
```

这样三类功能职责清晰：

> **新建决定知识库如何诞生，编辑管理基本属性，权限配置管理谁能使用以及能做什么。**
