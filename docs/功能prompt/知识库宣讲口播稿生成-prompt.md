口播稿必须**以业务需求和系统需求为主线**：先讲“业务上要解决什么问题（BR）”，再讲“系统里怎么落地（SR + 真实页面/按钮）”，形成“需求 → 实现”的对照闭环。凡引用需求点，请标注对应编号（如 BR-04 / SR-38），方便听众溯源。

### 三、约束

1. **禁止调用任何 Chrome / 浏览器调试工具**，也不要启动 dev server 去点页面；只通过**静态阅读代码**来核对功能。
2. 不要虚构不存在的功能；如果需求文档里写了但代码里没实现（或反之），请在稿子末尾的“需求-实现差异备注”里如实列出，不要在正文口播里编造。
3. 术语与角色命名保持与两份基线一致（普通员工 / 知识库管理员；仅查看 / 可上传 / 可管理；公共库 / 专业库 / 个人库）。

### 四、权限部分是重点（务必讲透）

权限是本次宣讲的核心，请**结合 `src/lib/knowledge/permission.ts` 与 `workbench/permission/`、`workbench/admin/PermissionConfigDrawer.tsx` 的真实实现**，把下面几条职责边界讲清楚：

1. **公共库 vs 专业库的权限差异**：两类库在“可见性、访问门槛、是否默认全员可访问、是否需要授权/申请”上的区别（对照 BR-01~BR-06、SR-04、第八章权限模型）。
2. **新建（Create）时的权限处理**：新建公共库与新建专业库在流程上的差异——公共库是否直接创建、专业库是否在新建流程中进入权限分配步骤（对照 SR-33、BR-40）。
3. **编辑（Edit）的职责边界**：编辑知识库只负责基本信息（名称、说明、分类、标签、类型），**不承载完整权限配置**（对照 SR-34、BR-41）。
4. **独立权限配置入口的职责**：权限配置作为独立入口/抽屉，从知识库列表的“权限”入口打开，负责角色授权、个人授权、成员管理、权限申请审批（对照 BR-36~BR-39、SR-38、权限模型 8.1/8.2）。
5. **授权对象与权限级别**：角色授权 + 个人授权如何叠加决定“最终可访问范围”；仅查看 / 可上传 / 可管理三级能力边界；以及不同文件状态下的可见性（待审批/已驳回/解析中/解析失败/已发布，对照第八章 8.3 与业务规则 5.1）。

用一句话能说清“**谁、在什么库、点哪个入口、能配置/得到什么权限**”，作为权限章节的收口。

#### 交付物 A：结合演示的口播稿（口播 + 演示脚本合一）

按“边演示边讲”的方式组织。建议结构：

1. 开场（模块定位 + 业务目标，1 分钟内）
2. 按页面/流程分段，每段包含三块：
