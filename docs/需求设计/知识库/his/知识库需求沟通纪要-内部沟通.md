# 知识库需求沟通纪要（老总沟通）

> **记录日期**：2026-07-06  
> **沟通性质**：需求阶段方向对齐 · 非 UI 定稿  
> **核心结论**：当前阶段**先理业务需求与系统需求，不做 UI 设计**；聚焦第一期可交付范围，其余记为潜在/后续需求。

---

## 一、总体原则

### 1.1 开发节奏：聚焦一期，敏捷迭代

| 原则 | 说明 |
|------|------|
| **范围收敛** | 一期必须划定明确边界，避免需求膨胀导致周期从 3 个月拖到 9 个月 |
| **快速出成果** | 目标尽快有可用的第一版，供内部测试、用户反馈、方向验证 |
| **分阶段交付** | 参考敏捷：约每 2 周一个迭代；第一版可「一个月快速版 → 第二月加功能 → 第三月再加功能」 |
| **先见成品再判断** | 即使经验丰富，对未知产品也需看到成品后才能确认路线是否正确 |
| **与瀑布项目区分** | 部分长期项目（如明年 9–10 月验收）可走瀑布式；**当前项目**强调早交付、早验证 |

### 1.2 需求分层（必须按顺序推进）

```
业务需求 → 系统需求 → UI 设计 → 开发
```

| 层级 | 内容 | 当前状态 |
|------|------|----------|
| **业务需求** | 用户要做什么：上传、查看、审批、收藏……逐条列出 | **当前重点** |
| **系统需求** | 按系统实现角度归类模块（如「我的文档」合并上传+收藏+审批状态） | 下一步 |
| **非功能性需求** | 权限模型、性能（如 2 秒打开）、解析失败处理机制等 | 与系统需求同步 |
| **UI 设计** | 在功能闭环、角色流程明确后再做；UI 过程中可能反哺系统需求调整 | **现阶段不做** |

> **警示**：若直接跳到 UI/实现，易导致需求频繁变更、返工、概念混乱。

### 1.3 需求方法论建议

- 使用 **UML 用例图（Use Case）**：明确角色（小人）及其可执行的操作（Case）
- 每个需求需闭环：有上传就要有审批流程、审批人、状态推送；有查看就要有权限规则
- 需求整理完成后**逐条核对闭环**，避免「有功能无流程、有流程无角色」

## 二、多电厂 / 多客户需求管理

### 2.1 需求文档策略

| 场景 | 文档策略 |
|------|----------|
| **公共能力** | 先写**一份通用需求文档**（当前阶段） |
| **电厂特定需求** | 单独起文档，与公共需求区分 |
| **长期演进** | 需考虑多版本/多分支管理（见 2.2） |

### 2.2 需求采纳判断标准（商务 + 通用性）

当其他电厂提出新需求时，从以下维度衡量是否纳入系统：

| 维度 | 倾向采纳 | 倾向不采纳 / 延后 |
|------|----------|-------------------|
| **通用性** | 多电厂均会用，对后续产品化有帮助 | 仅某一电厂特有，其他厂无此场景 |
| **商务投入** | 费用与需求范围匹配 | 「十块钱想买一千块的东西」——超出合同/投入边界 |
| **底层影响** | 可作为插件/独立模块，不破坏现有架构 | 需重写底层、影响已交付功能的大改 |
| **阶段匹配** | 符合一期基础目标 | 不符合一期目标 → **先记录，不实施** |

> **产品化方向**：尽量将电厂特定需求在需求层面融合为统一标准能力，而非为单厂定制。

### 2.3 多版本 / 多分支技术考量（后续）

- 公共模块（知识库、考试、能力提升等）需**封装良好**，各厂定制尽量拉分支、互不影响
- 若分支间共享公共代码，缺陷修复需合并多分支——维护成本高，故需求层优先标准化
- 模块应**高内聚**：如考试模块独立，缺陷只改考试模块

## 三、知识库：信息架构调整（重要变更）

### 3.1 现有设计问题

当前设计：知识库首页左侧为 **「我的空间 + 公共空间 + 部门空间」** 并列菜单。

**老总意见**：此结构**无法满足**核心用户场景，需调整。

### 3.2 核心用户场景（昨天电话已确认）

> **用户希望能一次性看到「自己有权限访问的全部文档」**，而不是逐个知识库点进去找。

- 例：公共空间小 A 库、小 B 库，部门大 A 库及其子库，合计 50–70 篇文档——用户希望有一个界面**汇总列出全部可访问文档**
- 支持按分类/条件**过滤**，而非强制先选空间再选库

### 3.3 推荐信息架构（v1.1 修订）

> **修订说明**：「所有文档」为**按钮/二级菜单入口**（跨库文件汇总），非首页主体；默认落地页为**知识库首页**。

#### 页面结构

| 页面 | 结构 |
|------|------|
| **知识库首页**（默认） | 左：我的 / 快速访问 / 知识库树 → 右：选中库的文件列表 |
| **所有文档** | 按钮或二级菜单进入；跨库文件汇总 + 筛选，无左侧树 |
| **文件详情页** | 左：当前库文件列表 → 中：预览 → 右：AI 辅助；顶：返回首页 |

#### 知识库首页左侧栏

```
我的              → 跳转二级菜单「我的文档」
快速访问
  📁 个人知识库    → 跳转「我的文档 → 个人知识库」
  📁 常用库…
知识库树
  📂 分类一
    📁 知识库 A
    📁 知识库 B
  …
```

#### 系统二级菜单

```
知识库（一级）
├── 知识库首页（默认）
├── 所有文档
├── 我的文档
└── 知识库管理（管理员）
```

~~原「左侧所有+分类树、右侧全部文档」方案~~ → 已调整为「首页按库浏览 + 所有文档独立汇总页」。

### 3.4 关于「部门空间」

| 原设计 | 调整后 |
|--------|--------|
| 部门作为空间层级 | **弱化部门层面概念** |
| 部门下挂知识库 | 知识库按**专业/分类**组织；部门从组织架构引用，非用户手动「新建部门」 |
| 新建部门 | 属于**组织架构维护**，非知识库模块职责 |

> 实际电厂场景：多为「运行专业库」「某某专业库」等专业维度，而非按部门行政划分。

### 3.5 管理员 vs 普通用户界面分离

| 角色 | 界面 |
|------|------|
| **普通用户** | 文档查看、上传、收藏、过滤——一个清爽的浏览界面 |
| **管理员** | 独立管理入口：新建知识库、分类维护、权限配置等 |
| **同一人兼两角色** | 管理员登录后可见管理菜单，与普通浏览不混在同一操作流 |

新建知识库时：

- 弹窗/独立页需明确显示**上级分类**，用户能看清建在哪里
- 实施阶段很可能由实施人员代维，电厂用户主动建库意愿低

## 四、知识库：文件与元数据

### 4.1 知识库内不设「目录树」

| 层级 | 是否有目录 |
|------|------------|
| 知识库之上 | **有**分类层次（可嵌套） |
| 知识库内的文件 | **无**独立目录树 |

文件组织方式：

- **标签 / 专业类型**等元数据属性
- 界面顶部标签过滤，而非 Windows 式文件夹目录树

### 4.2 「库内目录树」为潜在需求（暂不实施）

提出场景：拖放上传到指定目录、列表按目录展示。

**暂不做的原因**：

1. 与「智能自动打标签」方向冲突——上传还要手动选目录，增加负担
2. 多知识库间目录结构可能重叠，每库重建目录体验差
3. 属展示便捷性，现有「分类 + 知识库 + 标签过滤」可覆盖主要场景

> **结论**：记录为潜在需求，**第二阶段及以后**再评估。

### 4.3 专业类型

- 指电力行业领域专业分类（非 PDF/Word 文件格式）
- 作为元数据/标签属性即可，**无需单独建「目录」层级**

## 五、功能分期规划

### 5.1 第一期（必须做好）

聚焦「存得住、找得到、管得住」，基本功能补齐：

| 序号 | 功能 | 备注 |
|------|------|------|
| 1 | 文档上传 | 含审批流程 |
| 2 | 文档查看 / 预览 | 权限控制 |
| 3 | 我的文档 | 上传记录、审批状态、收藏等合并入口 |
| 4 | **查看全部可访问文档** | 默认「所有」汇总列表 + 分类过滤 |
| 5 | 知识库权限设置 | 按用户/角色分配；支持角色级授权 |
| 6 | 无权限知识库可见 + 申请权限 | 可选灰色展示 |
| 7 | 文档下载 | — |
| 8 | 列表状态持久化 | 如树形展开状态保存 |
| 9 | 解析失败处理 | 见 5.3 |
| 10 | 审批消息推送 | 审批通过/驳回通知 |
| 11 | 收藏 | 实现简单但需考虑入口统一 |

**第一期明确不做 / 不展开**：

- 库内目录树
- 文件对比、文件权威解读（见 5.2）
- 移动端
- 智能专题配置等跨模块智能能力（与考试等模块另议）

### 5.2 后续阶段（潜在需求，先记录）

| 功能 | 阶段建议 | 场景说明 |
|------|----------|----------|
| **文件版本差异对比** | 二期第二～四阶段 | 年度规程/考核规则修订，对比新旧版本差异；可在预览页下方展示历史版本入口，打开新界面做 diff；**插件式功能，不影响底层** |
| **文件权威解读** | 更往后 | 条文解读需结合领域知识，不能仅靠大模型推理；可做「发布解读 → 全员更新」的通用能力，实现方案未定 |
| **库内目录树** | 二期及以后 | 展示便捷，非刚需 |
| **原文定位 / 解析标记** | 视一期是否预留 | 智能问答需定位到原文位置；若一期要做问答联动，可能需一期考虑底层标记；否则二期重构 |
| **文件预览增强** | 参考乐享等平台 | 一期先把基础预览 + 权限做顺 |

### 5.3 解析失败处理（需在设计中明确）

| 方案 | 说明 |
|------|------|
| **用户侧重试** | 上传者看到失败标识，一键重解析——但多数用户不懂技术，要求过高 |
| **管理员统一处理** | 管理界面展示解析失败列表，定时任务扫描重试 |
| **建议** | 非功能性需求先写入设计；实现可分期，但**流程与角色要先定义** |

## 六、与现有需求文档的差异对照

| 现有设计（v0.3 等） | 本次沟通调整方向 |
|---------------------|------------------|
| 左侧「我的 + 公共空间 + 部门空间」并列 | 改为「所有 + 分类树」，弱化空间菜单 |
| 空间 → 知识库 → **库内目录** → 文件 | 去掉库内目录层，文件用标签/专业类型过滤 |
| 知识库仅一级系统菜单 | 增加二级菜单（所有文档、我的文档等） |
| 新建部门在知识库内 | 部门走组织架构，不在知识库维护 |
| 拖放到库内目录 | 暂缓；优先智能打标签 |
| 文件对比写在建设计划 | 明确为二期以后潜在需求 |

## 七、竞品与定位

- 可参考：乐享、腾讯、网易等知识库/协作产品（设计可借鉴，不必照搬）
- 实事求是梳理**相对竞品优势**（如与腾讯某产品对标时的差异化）
- 在效率与时间约束下，**先把基本功能做全、做顺**，再谈超越

## 九、名词统一

| 术语 | 含义 |
|------|------|
| **一级 / 二级 / 三级菜单** | 均指**系统主导航**，非页面内模块 |
| **分类** | 知识库之上的组织维度，可嵌套，下挂知识库 |
| **知识库** | 存放文档的容器 |
| **标签 / 专业类型** | 文件级元数据，用于过滤，非目录树 |
| **我的文档** | 系统功能模块：上传、收藏、审批状态等合集 |
| **所有（默认视图）** | 当前用户可访问的全部文档汇总列表 |

## 十、附录：沟通过程中的关键原话摘要

1. *「你现在先整理业务需求，整理业务需求时，先不考虑设计。」*
2. *「我希望能看到的所有文档……默认就显示这个你能看到的所有知识库。」*
3. *「知识库只有一个一级菜单，我觉得不合适。」*
4. *「新建知识库是管理员干的事情，不是用户。」*
5. *「不符合基础目标的，先记录；第一步要实现的东西先拿出来。」*
6. *「如果需求很通用，对以后都有帮助，可能答应采纳；如果只有你这一个厂特定，可能就不考虑。」*
7. *「文件对比确实有这个需求，但可以放在第二阶段、第三阶段或第四阶段。」*
